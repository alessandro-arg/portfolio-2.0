In the last post I talked about filesystem and package management. This week I spent more time learning how files work, view file contents, search for text, and understand file informations in a simple way. <br />
Not editing files yet. More like understanding how to inspect them, search through them and figure out what is happening on the system itself.

I wanted to explore the `/etc` directory a bit more and understand how people actually investigate Linux systems from the terminal. I watched some videos from Mischa van den Burg, who explains Linux and DevOps topics in a very practical way.

Normally, if I want to open a file like .xlsx on Windows, I need Excel or another GUI application. On Linux, you can inspect a lot of things directly from the terminal without opening a graphical program first. That still feels weird to me sometimes, but also really powerful.

## What I did

The first commands I played around with were `cat` and `grep`.

`cat` simply prints the file content into the terminal.

```bash
cat /etc/passwd
```

That sounds basic, but it changes how you interact with a system. When working on servers, especially without a desktop environment, being able to inspect files quickly becomes really important.

We also have `head` and `tail`. <br />
By default they show the first or last 10 lines, but you can customize it:

```bash
head -20 /etc/passwd
tail -20 /etc/passwd
```

The command that stood out the most for me was this one:

```bash
tail -f /var/log/syslog
```

The `-f` means follow. <br />
So instead of printing the file once, Linux keeps watching the file and updates the terminal in real time whenever something changes.

Watching logs live like this felt really cool honestly. I immediately understood why people use this for debugging servers and applications.

I also spent a lot of time experimenting with `grep`.

```bash
grep "error" /var/log/syslog
```

This searches for all lines containing `"error"`.

Then I tried different flags:

- `grep -i` → ignores uppercase and lowercase, finds lines with "ERROR" too
- `grep -n` → show line numbers
- `grep -v` → show lines that do NOT match
- `grep -r` → search recursively through directories
- `grep -c` → count the matches
- `grep -B` and `grep -A` → show the lines before or after the match
- `grep -C` → combines the -B and the -A flags

I also learned that `grep` supports patterns and not only plain text.

- `^` → means 'starts with' ("^error")
- `$` → means 'ends with' ("err$")
- `[0-9]` → matches any digits

I definitely need more practice with patterns and regex later, but I can already see how useful this is.

Another thing I was wondering was:

## What type of file is this?

For that I used the `file` command:

```bash
file /bin/ls
```

Output:

```bash
/bin/ls: ELF 64-bit LSB pie executable, ARM aarch64, version 1 (SYSV),
dynamically linked, interpreter /lib/ld-linux-aarch64.so.1,
BuildID[sha1]=19a53698c72a1d765f961ccd04bff6665434c0f5,
for GNU/Linux 3.7.0, stripped
```

I found this super interesting. <br />
You immediately see:

- executable type
- CPU architecture
- linking information
- operating system target

Without opening anything.

For even more details, I used `stat`.

```bash
stat /etc/passwd
```

This shows permissions, timestamps, ownership, inode information and much more:


### Words, Lines and Characters

For this, we got `wc`.

```bash
wc /etc/passwd
```

And the flags:

- `wc -l`
- `wc -w`
- `wc -c`

For counting lines, words and characters separately.

### Disk usage & Disk free

At the end I explored storage related commands:

- `du -sh` → disk usage
- `df -sh` → disk free space

The `-h` flag makes the output human-readable, which is definitely easier to understand than raw bytes, and the `-s` flag to summarize the output.

The `df` command shows all mounted filesystems and their space usage. <br />
I can already tell these commands will become part of my daily workflow later.

## What I learned

Most of the session was exploration and experimentation. <br />
I mainly tried commands against real directories and logs to better understand what they actually do.

Now I slowly understand why Linux administrators and DevOps engineers work so heavily in the shell. You can inspect almost everything directly from the command line without needing a GUI.

A few things that stood out to me:

- logs become much easier to inspect with `tail -f`
- `grep` is insanely powerful
- Linux exposes a lot of system information directly through files
- commands like `stat`, `file`, `du` and `df` help understand what is actually happening on the machine
